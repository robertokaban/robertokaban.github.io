Pendahuluan #

Bayangkan Anda mentransfer uang antar dua rekening: saldo rekening A berkurang, lalu saldo rekening B bertambah. Jika server mati setelah pengurangan A tetapi sebelum penambahan B, uang “hilang” — data menjadi tidak konsisten.

Transaksi mencegah hal ini. Transaksi memastikan sekumpulan operasi dieksekusi sebagai satu kesatuan: berhasil semua (commit) atau gagal semua (rollback). Sifat-sifat inilah yang dijamin oleh ACID.

Artikel ini membahas cara menggunakan transaksi, isolation level, dan locking di MySQL. Semua contoh menggunakan skema toko_online dengan storage engine InnoDB (satu-satunya engine MySQL yang mendukung transaksi penuh).

Asumsi: Anda berada di database toko_online (USE toko_online;) dan tabel menggunakan engine InnoDB.

Apa itu Transaksi? #

Transaksi adalah urutan satu atau lebih perintah SQL yang diperlakukan sebagai satu unit kerja. Transaksi dimulai dengan START TRANSACTION dan diakhiri dengan COMMIT (menyimpan) atau ROLLBACK (membatalkan).

Contoh Sederhana #

START TRANSACTION;

UPDATE produk SET stok = stok - 1 WHERE id = 1;
INSERT INTO detail_pesanan (pesanan_id, produk_id, jumlah, harga_satuan)
VALUES (1, 1, 1, 1500000.00);

COMMIT;

Jika salah satu perintah gagal, kita bisa ROLLBACK untuk membatalkan semua perubahan.

ACID: Empat Jaminan Transaksi #

ACID adalah akronim dari empat properti yang menjamin keandalan transaksi.

1. Atomicity (Atomisitas) #

Semua atau tidak sama sekali. Jika satu perintah dalam transaksi gagal, seluruh transaksi dibatalkan.

Contoh: transfer saldo — pengurangan dan penambahan harus terjadi bersamaan. Jika satu gagal, keduanya dibatalkan.

2. Consistency (Konsistensi) #

Transaksi membawa database dari satu keadaan valid ke keadaan valid lainnya. Constraints (PRIMARY KEY, FOREIGN KEY, CHECK, UNIQUE) tetap terjaga.

Contoh: FOREIGN KEY mencegah detail_pesanan merujuk pesanan_id yang tidak ada.

3. Isolation (Isolasi) #

Transaksi yang berjalan bersamaan tidak saling mengganggu. Setiap transaksi melihat dunia seolah-olah ia satu-satunya yang berjalan. Tingkat isolasi bisa diatur (dibahas di bagian Isolation Level).

4. Durability (Durabilitas) #

Setelah COMMIT, perubahan permanen — tetap ada meskipun server crash. InnoDB menjamin ini melalui write-ahead log (redo log) dan flush ke disk.

Perintah Transaksi di MySQL #

START TRANSACTION #

Memulai transaksi baru:

START TRANSACTION;

Atau:

BEGIN;

COMMIT #

Menyimpan semua perubahan secara permanen:

COMMIT;

ROLLBACK #

Membatalkan semua perubahan sejak START TRANSACTION:

ROLLBACK;

SAVEPOINT dan ROLLBACK TO SAVEPOINT #

Savepoint adalah titik penanda di dalam transaksi. Anda bisa rollback ke savepoint tertentu tanpa membatalkan seluruh transaksi.

START TRANSACTION;

INSERT INTO pelanggan (nama, email) VALUES ('Andi', 'andi@example.com');
SAVEPOINT sp1;

INSERT INTO pelanggan (nama, email) VALUES ('Budi', 'budi@example.com');
SAVEPOINT sp2;

INSERT INTO pelanggan (nama, email) VALUES ('Citra', 'citra@example.com');

-- Batalkan hanya insert Citra
ROLLBACK TO SAVEPOINT sp2;

COMMIT;

Hasil: Andi dan Budi tersimpan; Citra dibatalkan.

Menghapus savepoint:

RELEASE SAVEPOINT sp1;

SET autocommit #

Secara default, MySQL berjalan dalam mode autocommit — setiap perintah langsung di-commit. Untuk menggunakan transaksi eksplisit:

SET autocommit = 0;  -- matikan autocommit
-- ... perintah SQL ...
COMMIT;              -- simpan
-- atau ROLLBACK;
SET autocommit = 1;  -- aktifkan kembali

Tips: Kebanyakan aplikasi menggunakan START TRANSACTION eksplisit daripada mematikan autocommit, karena lebih jelas dan aman.

Melihat Status Transaksi #

SELECT @@autocommit;
SELECT @@transaction_isolation;

Contoh Nyata: Transfer Stok Antar Gudang #

Misalkan kita menambahkan tabel gudang dan stok_gudang:

CREATE TABLE gudang (
  id INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  nama VARCHAR(100) NOT NULL
);

CREATE TABLE stok_gudang (
  gudang_id INT UNSIGNED NOT NULL,
  produk_id INT UNSIGNED NOT NULL,
  jumlah INT NOT NULL DEFAULT 0,
  PRIMARY KEY (gudang_id, produk_id),
  FOREIGN KEY (gudang_id) REFERENCES gudang(id),
  FOREIGN KEY (produk_id) REFERENCES produk(id),
  CONSTRAINT chk_jumlah_gudang CHECK (jumlah >= 0)
);

Transfer 5 unit produk dari gudang 1 ke gudang 2:

START TRANSACTION;

-- Kurangi stok gudang asal
UPDATE stok_gudang
SET jumlah = jumlah - 5
WHERE gudang_id = 1 AND produk_id = 1;

-- Tambah stok gudang tujuan
UPDATE stok_gudang
SET jumlah = jumlah + 5
WHERE gudang_id = 2 AND produk_id = 1;

-- Verifikasi tidak ada stok negatif
-- (CHECK constraint akan menolak jika jumlah < 0)

COMMIT;

Jika UPDATE pertama gagal (misalnya stok tidak cukup dan CHECK menolak), seluruh transaksi bisa di-ROLLBACK, sehingga stok gudang tujuan tidak bertambah.

Contoh dengan Pengecekan Kondisi #

START TRANSACTION;

-- Cek stok tersedia
SELECT jumlah INTO @stok_tersedia
FROM stok_gudang
WHERE gudang_id = 1 AND produk_id = 1
FOR UPDATE;

-- Jika stok cukup, lanjutkan
-- (logika ini biasanya di aplikasi, bukan SQL murni)
UPDATE stok_gudang SET jumlah = jumlah - 5
WHERE gudang_id = 1 AND produk_id = 1;

UPDATE stok_gudang SET jumlah = jumlah + 5
WHERE gudang_id = 2 AND produk_id = 1;

COMMIT;

FOR UPDATE mengunci baris agar transaksi lain tidak mengubahnya sampai transaksi ini selesai (dibahas di bagian Locking).

Isolation Level #

Isolation level menentukan seberapa besar transaksi saling terisolasi. MySQL mendukung empat level (dari paling longgar ke paling ketat):

Level Dirty Read Non-Repeatable Read Phantom Read
READ UNCOMMITTED ✅ Mungkin ✅ Mungkin ✅ Mungkin
READ COMMITTED ❌ Tidak ✅ Mungkin ✅ Mungkin
REPEATABLE READ (default) ❌ Tidak ❌ Tidak ⚠️ Mungkin (di InnoDB dicegah via next-key lock)
SERIALIZABLE ❌ Tidak ❌ Tidak ❌ Tidak

Penjelasan Fenomena #

  • Dirty Read — membaca data yang belum di-commit oleh transaksi lain (bisa berubah jika transaksi itu rollback).
  • Non-Repeatable Read — membaca baris yang sama dua kali dalam satu transaksi menghasilkan nilai berbeda (karena transaksi lain mengubahnya).
  • Phantom Read — menjalankan query yang sama dua kali menghasilkan jumlah baris berbeda (karena transaksi lain menambah/menghapus baris).

Melihat Isolation Level #

SELECT @@transaction_isolation;

Mengubah Isolation Level #

Untuk sesi saat ini:

SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;

Untuk transaksi berikutnya saja:

SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
START TRANSACTION;
-- ...
COMMIT;

Secara global (semua koneksi baru):

SET GLOBAL TRANSACTION ISOLATION LEVEL READ COMMITTED;

Tips: Default MySQL adalah REPEATABLE READ, yang cocok untuk sebagian besar aplikasi. Gunakan READ COMMITTED jika aplikasi Anda banyak melakukan update bersamaan dan toleran terhadap non-repeatable read (misalnya aplikasi web modern). SERIALIZABLE sangat ketat tetapi paling lambat — jarang dipakai.

Contoh Perbedaan Isolation Level #

Sesi A:

SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
START TRANSACTION;
SELECT total FROM pesanan WHERE id = 1;
-- hasil: 100000

Sesi B:

UPDATE pesanan SET total = 200000 WHERE id = 1;
COMMIT;

Sesi A (masih dalam transaksi):

SELECT total FROM pesanan WHERE id = 1;
-- READ COMMITTED: 200000 (non-repeatable read terjadi)
-- REPEATABLE READ: 100000 (nilai awal tetap)

Pada REPEATABLE READ, MySQL menggunakan MVCC (Multi-Version Concurrency Control) sehingga sesi A tetap melihat snapshot data saat transaksi dimulai.

Locking #

Lock mencegah konflik antar transaksi yang mengakses data yang sama.

Jenis Lock #

Lock Keterangan
Shared Lock (LOCK IN SHARE MODE / FOR SHARE) Bisa dibaca banyak transaksi, tetapi tidak bisa diubah sampai lock dilepas
Exclusive Lock (FOR UPDATE) Hanya transaksi pemegang lock yang bisa membaca dan mengubah baris

Contoh FOR UPDATE #

Mengunci baris yang dibaca agar transaksi lain tidak bisa mengubahnya:

START TRANSACTION;

SELECT jumlah FROM stok_gudang
WHERE gudang_id = 1 AND produk_id = 1
FOR UPDATE;

-- Baris terkunci sampai COMMIT/ROLLBACK
UPDATE stok_gudang SET jumlah = jumlah - 5
WHERE gudang_id = 1 AND produk_id = 1;

COMMIT;

Transaksi lain yang mencoba SELECT ... FOR UPDATE atau UPDATE pada baris yang sama akan menunggu sampai lock dilepas.

Contoh FOR SHARE #

Mengizinkan transaksi lain membaca tetapi tidak mengubah:

START TRANSACTION;

SELECT jumlah FROM stok_gudang
WHERE gudang_id = 1 AND produk_id = 1
FOR SHARE;

-- Transaksi lain bisa membaca (FOR SHARE) tetapi tidak bisa UPDATE
COMMIT;

Lock Timeout #

Jika transaksi menunggu lock terlalu lama, MySQL akan menghasilkan error:

ERROR 1205 (HY000): Lock wait timeout exceeded; try restarting transaction

Atur timeout (detik):

SET SESSION innodb_lock_wait_timeout = 10;

Deadlock #

Deadlock terjadi jika dua transaksi saling menunggu lock yang dipegang oleh transaksi lain.

Contoh:

  • Transaksi A mengunci baris 1, lalu ingin mengunci baris 2.
  • Transaksi B mengunci baris 2, lalu ingin mengunci baris 1.
  • Keduanya menunggu selamanya.

MySQL mendeteksi deadlock dan otomatis me-ROLLBACK salah satu transaksi dengan error:

ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction

Melihat deadlock terakhir:

SHOW ENGINE INNODB STATUS\G

Cari bagian LATEST DETECTED DEADLOCK.

Mencegah deadlock:

  • Akses tabel/baris dalam urutan yang konsisten di semua transaksi.
  • Jaga transaksi tetap singkat.
  • Gunakan isolation level yang sesuai.
  • Tangani error deadlock di aplikasi dengan retry.

Transaksi dan DDL #

Di MySQL, sebagian besar perintah DDL (CREATE, ALTER, DROP, TRUNCATE) menyebabkan implicit commit — transaksi yang sedang berjalan otomatis di-commit sebelum DDL dieksekusi.

START TRANSACTION;
INSERT INTO pelanggan (nama, email) VALUES ('Test', 'test@example.com');

-- DDL menyebabkan implicit commit
CREATE TABLE test_table (id INT);

ROLLBACK;  -- INSERT di atas TIDAK dibatalkan!

⚠️ Peringatan: Jangan mencampur DDL dengan DML dalam satu transaksi jika Anda mengandalkan ROLLBACK.

Transaksi dalam Aplikasi #

Saat menggunakan MySQL dari aplikasi (PHP, Python, Node.js, dll.), transaksi dikelola melalui API driver:

PHP (PDO):

$pdo->beginTransaction();
try {
    $pdo->exec("UPDATE stok_gudang SET jumlah = jumlah - 5 WHERE ...");
    $pdo->exec("UPDATE stok_gudang SET jumlah = jumlah + 5 WHERE ...");
    $pdo->commit();
} catch (Exception $e) {
    $pdo->rollBack();
    throw $e;
}

Python (mysql-connector):

conn.start_transaction()
try:
    cursor.execute("UPDATE stok_gudang SET jumlah = jumlah - 5 WHERE ...")
    cursor.execute("UPDATE stok_gudang SET jumlah = jumlah + 5 WHERE ...")
    conn.commit()
except Exception:
    conn.rollback()
    raise

Node.js (mysql2):

const conn = await pool.getConnection();
await conn.beginTransaction();
try {
    await conn.execute("UPDATE stok_gudang SET jumlah = jumlah - 5 WHERE ...");
    await conn.execute("UPDATE stok_gudang SET jumlah = jumlah + 5 WHERE ...");
    await conn.commit();
} catch (err) {
    await conn.rollback();
    throw err;
} finally {
    conn.release();
}

Prinsipnya sama: begin → operasi → commit/rollback, dengan try/catch untuk menangani error.

Best Practice Transaksi #

  1. Jaga transaksi tetap singkat. Transaksi panjang mengunci baris lebih lama dan meningkatkan risiko deadlock.

  2. Jangan menunggu interaksi user di dalam transaksi. Jika user harus mengisi form, jangan buka transaksi sebelum data lengkap.

  3. Tangani deadlock dengan retry. Deadlock adalah hal normal di sistem konkuren; aplikasi harus bisa mencoba ulang.

  4. Gunakan isolation level yang sesuai. Default REPEATABLE READ cocok untuk sebagian besar kasus; READ COMMITTED untuk aplikasi dengan banyak update.

  5. Hindari DDL di dalam transaksi DML. DDL menyebabkan implicit commit.

  6. Gunakan FOR UPDATE dengan bijak. Kunci hanya baris yang benar-benar akan diubah.

  7. Pantau transaksi panjang. Query berikut membantu menemukan transaksi yang berjalan lama:

SELECT trx_id, trx_state, trx_started,
       TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS durasi_detik,
       trx_query
FROM information_schema.innodb_trx
ORDER BY trx_started;
  1. Rollback transaksi yang menggantung. Jika ada transaksi macet, identifikasi dan KILL:
KILL <thread_id>;

Ringkasan #

Perintah / Konsep Fungsi
START TRANSACTION / BEGIN Memulai transaksi
COMMIT Menyimpan perubahan permanen
ROLLBACK Membatalkan semua perubahan
SAVEPOINT Titik rollback di dalam transaksi
ROLLBACK TO SAVEPOINT Rollback ke savepoint tertentu
SET autocommit Mengatur mode autocommit
FOR UPDATE Exclusive lock pada baris
FOR SHARE Shared lock pada baris
Isolation level Mengatur tingkat isolasi transaksi

ACID:

  • Atomicity — semua atau tidak sama sekali.
  • Consistency — data tetap valid sesuai constraints.
  • Isolation — transaksi tidak saling mengganggu.
  • Durability — perubahan permanen setelah COMMIT.

Poin penting:

  • Hanya InnoDB yang mendukung transaksi penuh di MySQL.
  • Default isolation level adalah REPEATABLE READ.
  • DDL (CREATE, ALTER, DROP) menyebabkan implicit commit.
  • Deadlock adalah hal normal — tangani dengan retry di aplikasi.
  • Jaga transaksi tetap singkat dan gunakan lock seperlunya.
